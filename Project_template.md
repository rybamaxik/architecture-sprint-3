# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

В настоящий момент монолитный бэкенд обеспечивает следующие возможности для пользователей:
- включение/отключение системы отопления;
- установка требуемой пользователем целевой температуры.

Бэкенд обеспечивает также возможность подключения новых экземпляров систем отопления.

**Мониторинг температуры:**

В настоящий момент монолитный бэкенд обеспечивает возможность запроса пользователями текущего значения температуры с датчиков, установленных в экземплярах систем отопления.

### 2. Анализ архитектуры монолитного приложения

В настоящий момент монолитный бэкенд представляет собой приложение на языке программирования Java, написанное с использованием фреймворка Spring Boot. В качестве базы данных используется PostgreSQL.

За управление системами отопления отвечает класс HeatingSystemController. Он реализует поддержку следующих эндпоинтов (все расположены внутри пути /api/heating):
- /{id} -- методы GET и PUT позволяют получить объект системы отопления, имеющей идентификатор равный числу id, как DTO (Data Transfer Object). DTO имеет поля - идентификатор id, булевский флаг включения системы isOn, дробные числа целевой температуры (targetTemperature) и текущей температуры (currentTemperature);
- /{id}/turn-(on|off) - методы POST позволяют включить (эндпоинт turn-on) и выключить (эндпоинт turn-off) систему отопления с идентификатором id;
- /{id}/set-temperature - метод POST позволяет установить целевую температуру для системы отопления с идентификатором id;
- /{id}/current-temperature - метод GET позволяет получить текущую температуру с датчика системы отопления, имеющую идентификатор id.

Внутри HeatingSystemController есть объект, реализующий интерфейс HeatingSystemService и логгер.

HeatingSystemService - внутренняя служба управления системами отопления. Содержит основные методы, реализующие требуемый для описанных выше эндпоинтов функционал. Также содержит JPA репозиторий для хранения состояний систем отопления, который (насколько я понимаю) должен работать с таблицей heating_systems в БД. Судя по всему, была у авторов кода была идея завести JPA репозиторий для хранения показателей датчиков температуры (для чего в БД заведена таблица temperature_sensors), но эту идею не довели до конца.

Также не реализована бизнес-логика поддержания температуры на заданном уровне.

База данных на основе PostgreSQL содержит две вышеупомянутые таблицы - heating_systems (содержит состояние систем отопления в виде идентификатора экземпляра системы отопления, флаг включения, целевую и текущую температуры) и temperature_sensors (содержит показания датчиков температуры в виде идентификатора датчика, текущее показание температуры от него и время последнего обновления показания).

### 3. Определение доменов и границы контекстов

В результате анализа требований бизнеса и предметной области можно выделить один домен (управление умным домом) и несколько его поддоменов:

- поддомен конфигурации умных домов и устройств
- поддомен управления и мониторинга устройств умного дома
- поддомен автоматизации

В настоящий момент в бэкенде реализовано решение, попадающее только в поддомен управления и мониторинга устройств умного дома. Бэкенд через запрос получает от датчиков устройств отопления значение текущей температуры, дает команды на включение/отключение системы отопления, а также на установку нужной температуры на устройства отопления.

Предложенное решение будет включать части, относящиеся ко всем трем поддоменам.

Границы контекста:
Системой "Теплый дом" пользуются клиенты, а специалисты по обслуживанию оказывают техническую поддержку. Клиенты регистрируются, добавляют дома и находящиеся в них устройства - в мобильном приложении или через веб-интерфейс. Клиенты также умеют просматривать текущее и прошлое состояние устройств (выключены, включены, параметры их работы), а также данные с датчиков этих устройств. Клиенты управляют устройствами вручную, а также настраивают сценарии автоматизации. Специалистам по обслуживанию, кроме вышеперечисленного функционала, доступна также расширенная телеметрия.

Система "Теплый дом" взаимодействует с устройствами и датчиками по стандартным протоколам. От устройств и датчиков в систему поступают показатели (текущая температура, состояние, и т.д.), а также расширенная телеметрия, доступная техподдержке. От системы в адрес устройств и датчиков поступают запросы и управляющие воздействия (команды на включение/выключение, изменение параметров работы, и т.п.).

### **4. Проблемы монолитного решения**

- добавление новых устройств (например, систем отопления) невозможно без участия техподдержки;
- бэкенд не может масштабироваться ни вертикально, ни горизонтально;
- добавление новых типов устройств потребует переписывания изрядной части кода;
- отсутствует поддержка автоматизации.

### 1. Тип API

Для всех микросервисов, кроме AuthService (сервис аутентификации и авторизации), имеет смысл использовать Async API, поскольку все остальные микросервисы работают с шлюзами умного дома и устройствами, которые к шлюзам подключены. Связь с шлюзом может быть нестабильной, шлюз и устройства могут работать медленно, поэтому использовать синхронные API - значит, обрекать себя на частое длительное ожидание ответа, что в среднем заметно может ухудшить отзывчивость системы.
